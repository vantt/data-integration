# Materialization Configuration

> dbt materialization strategies for DuckDB + Parquet

## Overview

Different model layers use different materialization strategies optimized for their purpose:

| Layer | Materialization | Storage | Purpose |
|-------|-----------------|---------|---------|
| Sources (`src_`) | **Incremental** | DuckDB table | JSON extraction + dedup + accumulation |
| Staging (`stg_`) | View | None | Enrichment joins, unnest |
| Standard (`std_`) | View | None | Business normalization, status mapping |
| Intermediate (`int_`) | Incremental / Ephemeral | DuckDB | Cross-entity metrics |
| Marts | External (Parquet) | Parquet files | Serving layer |

## Materialization Types

### View

**Use for:** Sources, staging models

```sql
{{ config(materialized='view') }}

SELECT * FROM read_parquet(...)
```

**Characteristics:**
- No data storage
- Always fresh (reads source directly)
- Slower queries (recomputes each time)

### Table

**Use for:** Lookup tables, small dimensions

```sql
{{ config(materialized='table') }}

SELECT * FROM {{ ref('source') }}
```

**Characteristics:**
- Stored in DuckDB file
- Fast queries
- Stale until refreshed

### Incremental

**Use for:** Large staging/fact tables

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert'
) }}

SELECT * FROM {{ ref('source') }}
{% if is_incremental() %}
WHERE event_timestamp > (SELECT MAX(event_timestamp) FROM {{ this }})
{% endif %}
```

**Characteristics:**
- Only processes new/changed data
- Much faster for large tables
- Requires careful logic

### External (Parquet)

**Use for:** Marts exported to serving layer

```sql
{{ config(
    materialized='external',
    location='{{ env_var("DBT_EXPORT_PATH") }}/fact_orders/'
) }}

SELECT * FROM {{ ref('int_orders_enriched') }}
```

**Characteristics:**
- Writes to Parquet files
- Portable (no DuckDB dependency)
- Enables rolling snapshots

### Ephemeral

**Use for:** Intermediate logic reused in multiple models

```sql
{{ config(materialized='ephemeral') }}

-- This becomes a CTE in downstream models
SELECT * FROM {{ ref('source') }}
```

**Characteristics:**
- No storage
- Compiled as CTE
- Good for DRY code

### dbt_project.yml (conceptual)

```yaml
models:
  sapo_analytics:

      # Sources - incremental extraction (JSON extract + dedup)
      src_sapo_orders:
        +materialized: incremental  # extract JSON, tech+biz dedup, accumulate

        +materialized: view  # enrichment joins only

      stg_sapo_order_items:
        +materialized: view  # unnest from src_ extracted columns
      stg_sapo_customers:
        +materialized: incremental  # TODO: refactor to view on src_

    intermediate:
      +materialized: ephemeral
      +tags: ['intermediate']

      core:
        +materialized: external
        +tags: ['mart', 'core', 'olap']
      sales:
        +materialized: external
        +tags: ['mart', 'sales', 'olap']
```

## External Materialization

### Configuration

```sql
{{ config(
    materialized='external',
    location='{{ env_var("DBT_EXPORT_PATH") }}/dim_customers/',
    format='parquet',
    options={
        'partition_by': 'none',
        'overwrite': 'true'
    }
) }}
```

### Rolling Snapshots

For zero-downtime updates, use timestamped filenames:

```sql
{{ config(
    materialized='external',
    location='{{ env_var("DBT_EXPORT_PATH") }}/rolling/dim_customers/',
    format='parquet'
) }}

SELECT
    *,
    '{{ run_started_at.strftime("%Y%m%d_%H%M") }}' as _snapshot_ts
FROM {{ ref('stg_sapo_customers') }}
```

Output: `dim_customers/dim_customers_20260128_0400.parquet`

### Rolling Self-Refresh View Generation

Serving layer views auto-select latest snapshot:

```sql
-- Generated by scripts/provisioning/generate_serving_db.py
CREATE OR REPLACE VIEW dim_customers AS
SELECT * EXCLUDE (_snapshot_ts)
FROM read_parquet('/data_lake/export/marts/rolling/dim_customers/*.parquet')
WHERE _snapshot_ts = (
    SELECT MAX(_snapshot_ts)
    FROM read_parquet('/data_lake/export/marts/rolling/dim_customers/*.parquet')
);
```

## Incremental Strategy

### delete+insert (Recommended)

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert'
) }}

SELECT * FROM source
{% if is_incremental() %}
WHERE event_timestamp > (SELECT MAX(event_timestamp) FROM {{ this }})
{% endif %}
```

**Flow:**
1. Delete existing rows matching unique_key
2. Insert new rows
3. Atomic transaction

### merge

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}
```

**Note:** DuckDB merge support may vary. Test thoroughly.

### append

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='append'
) }}
```

**Use for:** Log-style tables where duplicates are acceptable.

## Performance Optimization

### Partition Pruning

Enable hive partitioning for source reads:

```sql
SELECT * FROM read_parquet(
    '{{ var("data_lake_path") }}/sapo_raw/order/**/*.parquet',
    hive_partitioning = true
)
-- Filter on partition columns
WHERE year >= '2025'
```

### Memory Management

```sql
{{ config(
    duckdb_config={
        'memory_limit': '4GB',
        'threads': 4
    }
) }}
```

### Incremental Window

Limit incremental lookback:

```sql
{% if is_incremental() %}
WHERE event_timestamp > (
    SELECT MAX(event_timestamp) - INTERVAL 1 DAY
    FROM {{ this }}
)
{% endif %}
```

## Full Refresh

### When to Full Refresh

- Schema changes
- Logic changes affecting historical data
- Data corruption recovery
- Periodic reconciliation

### Command

```bash
# Single model
python scripts/run_dbt.py run --select model_name --full-refresh

# All models
python scripts/run_dbt.py run --full-refresh

# By tag
python scripts/run_dbt.py run --select tag:mart --full-refresh
```

### Automatic Full Refresh

```sql
{{ config(
    materialized='incremental',
    full_refresh=true  -- Always full refresh
) }}
```

## Troubleshooting

### Issue: External Write Fails

```
Error: Cannot write to location
```

**Solution:**
1. Check `DBT_EXPORT_PATH` environment variable
2. Verify directory exists and is writable
3. Check for locked files

### Issue: Incremental Not Working

**Symptoms:** Full table scanned every run

**Check:**
1. `is_incremental()` condition in model
2. `unique_key` is defined
3. Model was built at least once

### Issue: Memory Error

**Solution:**
1. Use incremental materialization
2. Reduce memory_limit
3. Process in smaller batches
