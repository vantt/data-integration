## CRITICAL CORRECTIONS to initial framing

1. **`crm/sync/duckdb_reader.py` is ALREADY fail-loud.** `MissingColumnError` class (`:32-33`); `_fetch()` except wrapper (`:220-229`) re-raises column-missing as `MissingColumnError`, re-raises everything else. NO silent-skip. `_check_columns()` (`:194-209`) raises on mismatch.
2. **`reverse_etl_warehouse_to_crm.run()` is already all-or-nothing.** 8 `dr.fetch_*()` calls unguarded (`:161-168`) → any failure aborts whole run. `_run_step()` (`:50-82`) logs to `wh_sync_run` then re-raises.
3. **dbt contracts enforce at PARQUET-WRITE time, not at serving-view/consumer layer.** Serving views = `SELECT * EXCLUDE(filename)` glob (`bootstrap_serving_views.py:53-77`) → no type/column enforcement. Contract value = catch producer regression at `dbt build` in Dagster BEFORE bad parquet ships (fails asset → existing Lark `run_failure_sensor`). It does NOT add a runtime barrier for consumers.
4. **`transformation/exposures.yml` already exists** — 872 auto-generated entries, Metabase-only (`http://127.0.0.1:3001/...`). CRM/hug/Evidence/Rill/DetailView absent. Auto-generated by capture skill → do NOT hand-edit; use a SEPARATE curated file.

## Tier 1 — dbt contracts feasibility

- Versions: **dbt-core 1.11.8 / dbt-duckdb 1.10.1** (contracts since 1.5, versioned models since 1.6 → both supported). **NOT pinned** in `ingestion/requirements.txt` (bare `dbt-duckdb`) → floating-dep risk, pin first.
- `run_dbt.py:83` runs `dbt build` (run+test in one). Dagster: `dbt.cli(["build"], ...)` (`orchestration/assets/dbt.py:151`). Contract violation → `DbtRuntimeError` → failed asset → Lark.
- schema.yml all in one file `transformation/models/marts/schema.yml` (1393 lines):
  - `dim_customers` (`:159`) — most complete, 8 segmentation cols w/ data_type.
  - `fact_orders` (`:572`) — FK cols typed only; revenue cols untyped.
  - `mart_product_health` (`:1272`) — tests but NO data_type.
  - `mart_hug_optin` (`:5`) — weakest, not_null on token only.
  - **`mart_customer_tier` — NO ENTRY** (SQL at `models/marts/customer/mart_customer_tier.sql`).
  - **`mart_customer_action_queue` — NO ENTRY** (SQL at `models/marts/customer/mart_customer_action_queue.sql`).
- `dbt_project.yml:60` sets marts `+on_schema_change: sync_all_columns` → silently syncs drift, **conflicts with contract intent**. Override to `fail`/`append_new_columns` per contracted model.
- semantic layer `docs/analytics-handbook/semantic/` (7 files: dimensions/metrics/segments/freshness/entities/rules/README) = PROSE, not machine-readable. Source of truth for which data_types to declare.
- **OPEN (must spike):** does dbt-duckdb 1.10.x enforce `contract:{enforced:true}` on `materialized: external` (parquet) models, or only standard table materializations? Ambiguous in docs → empirical test required before committing.

## Tier 2 — serving snapshot + trigger

- `bootstrap_serving_views.py` — MANUAL only (no Dagster asset calls it), only writer to olap.duckdb (opens RW). View SQL `:53-77`. `main_marts` alias views `:146`. **Metabase-lock note `:8-23`**: current DuckDB version, Metabase read connection holds shared lock that BLOCKS exclusive writer ("Conflicting lock is held in PID 0", verified 2026-06-10) → must `docker compose stop metabase` before bootstrap. (Stale contradicting comment at `:94-97`.)
- `refresh_rolling.py` — runs every pipeline via `build_serving_db` asset; does NOT open olap.duckdb; GCs parquet + writes `.known_tables.json` (`:35`); emits `[!] SCHEMA_DRIFT` (`:148-155`) → `serving.py:121-128` raises → Lark.
- `build_standalone_export.py` + asset `serving.py:140-171`: opens olap.duckdb `ATTACH ... (READ_ONLY)` (lock-safe), enumerates `main` VIEWs, `CREATE TABLE x AS SELECT * FROM src.x` (self-contained, no parquet dep), atomic `os.replace` → `sapo_export_<ts>.duckdb` + `sapo_export_latest.duckdb`, GC keep=3. Output `data_lake/serving/standalone/`. Served by `data_fileserver` Caddy (`docker-compose.yml:121-141`, `files.lan.fwg.vn`). **Nightly only** (`definitions.py:195`).

  - **GAP:** no version sidecar; only filename ts. No TZ session set on base tables (values already materialized → ok for data).
- `crm_sync.py` `crm_cache_refresh` asset (`:25-96`): `@asset(deps=[build_serving_db])`; `POST crm:8090/admin/refresh`; 10s timeout (`CRM_REFRESH_TIMEOUT_SEC`); treats 200/202/409 ok, else WARNING; **never fails pipeline** (`:68-88`). No retry, no completion poll, no durable marker.
