# Red Team Review — Security Adversary — Worklist-Claim-Call-Log Flow Fixes Plan

Reviewer role: Security Adversary (attacker mindset) + Fact Checker.
Plan reviewed: `plans/260711-0838-worklist-claim-call-log-flow-fixes/plan.md` + all 7 phase files.
Method: grep/read verification of every cited symbol/file/line against current `crm/src` before writing findings.

## Findings

## Finding 1: No ownership check on resolve_action_ids / resolve_task_ids / complete_task_ids — cross-customer/cross-staff data destruction (IDOR)
- **Severity:** Critical
- **Location:** Phase 2 ("Resolve-Outcome Gating"), Phase 6 §6b ("Dismiss-session bắt buộc log") — both touch the same unguarded write path.
- **Flaw:** `execute_side_effects()` step 7 iterates `resolve_action_ids`/`resolve_task_ids` and calls `action_state.dismiss(aid, user_id=uid)` / `task_svc.transition_status(tid, "done")` for each id with **no check that `aid`/`tid` actually belongs to the `party_id` in the URL**. `SQLiteActionStateRepository.dismiss()` resolves `(party_id, action_type)` *from* the action_id independently (`action_state_repository.py:56-66`) — it never compares against a caller-supplied party_id. `TaskService.transition_status()` does `self._task_repo.get_by_id(task_id)` with no party filter (`task_service.py:175-186`). These ids arrive as a client-editable hidden `<input>` inside the M08 form (`modal_log_activity.html:115`) and, per Phase 6b, are also proposed to be **built into a GET query string** (`/modals/m08?party_id={party_id}&resolve_action_ids={comma-joined ids}`) and threaded straight through into that same hidden field.
- **Failure scenario:** Any authenticated CRM staff member opens devtools, edits the hidden `resolve_action_ids`/`resolve_task_ids` value (or crafts the M08 GET URL directly) to include action/task ids belonging to a **different customer's queue or a different staff member's claimed task**, then submits M08 for their own `party_id`. The handler dismisses/completes those foreign ids anyway — silently burning another staff's action-queue signal (including the 30-day `crm_action_dismissal` TTL) or marking someone else's task "done" with zero authorization check and zero indication in the UI that this happened. This directly undermines the exact signal-integrity guarantee findings #2, #3, #9, #10 in the source report are trying to protect, and Phase 6b's proposed fix ("route dismiss-session through the bulk-resolve path") **expands** reliance on this unguarded primitive instead of closing the gap — it treats "require a log" (the stated policy fix) as equivalent to "authorized", which it is not.
- **Evidence:**
  - `crm/src/application/activity_side_effects.py:170-183` — dismiss/transition_status loop, no party filter.
  - `crm/src/adapters/outbound/sqlite/action_state_repository.py:40-52,56-66` — `dismiss(action_id, user_id)` resolves party from the bare id.
  - `crm/src/application/task_service.py:175-186` — `transition_status(task_id, new_status)`, `get_by_id` with no ownership check.
  - `crm/src/adapters/inbound/web/screens/customer360/screen_customer_360_panels.py:296-306` — existing `handle_dismiss_session` has the identical gap (`action_state.dismiss(aid, user_id=None)` per submitted `action_ids`, no cross-check against `party_id`).
  - `plans/.../phase-06-claim-policy-findings.md:47` — proposes funneling more traffic through this exact unguarded mechanism as the "recommended" fix for finding #10.
- **Suggested fix:** Before dismissing/completing, resolve each id's true `party_id`/`assignee_user_id` server-side and reject (or silently skip + log) any id that doesn't match the request's `party_id` (for actions) or isn't owned/claimed by the acting staff (for tasks). This should land as a precondition of Phase 2, not be deferred — Phase 6b currently makes the exposure worse, not better.

## Finding 2: `handle_unclaim_customer` has no ownership check — Phase 6a increases reliance on it without flagging the gap
- **Severity:** High
- **Location:** Phase 6 §6a ("Claim-at-call-start").
- **Flaw:** `PATCH /worklist/customers/{party_id}/unclaim` (`screen_worklist.py:526-538`) never reads `_current_user_id(request)` and never verifies the caller is the staff who holds the claim — it unconditionally calls `task_claim.unclaim_customer_actions(party_id)` for whatever `party_id` is in the URL. Phase 6a explicitly designates this endpoint as the *entire* mitigation for the new earlier auto-claim: "Bỏ ngang → dùng Trả việc có sẵn để nhả — no new unclaim logic needed" (`plan.md:39`, `phase-06-claim-policy-findings.md:23`).
- **Failure scenario:** Because Phase 6a now claims a customer the instant any staff presses "Gọi" (not just after finalize), claimed-but-uncontacted customers exist for longer stretches and in higher volume. Any other authenticated staff member can `PATCH /worklist/customers/{party_id}/unclaim` on a colleague's actively-claimed customer at any time — releasing it back to the shared queue mid-call, letting a second staff claim and contact the same customer, or simply as griefing. The plan explicitly increases the window/volume where this pre-existing gap matters and does not add or even flag the missing check.
- **Evidence:** `crm/src/adapters/inbound/web/screen_worklist.py:526-538` (no `uid`/ownership check, contrast with `handle_assign_me` at `:440-451` which does check `_current_user_id`). `plans/.../plan.md:39`, `plans/.../phase-06-claim-policy-findings.md:19-23,45`.
- **Suggested fix:** Add an ownership check in `handle_unclaim_customer` (compare current claim's `assignee_user_id` to `_current_user_id(request)`, 403 on mismatch) before or alongside Phase 6a landing — the fix currently only makes claims easier to acquire, not correspondingly harder to steal-release.

## Finding 3: `task_id` is an unauthenticated client-supplied Form field used as the sole gate to skip Phase 6a's new auto-claim — trivially spoofable, defeats the fix's own stated purpose
- **Severity:** High
- **Location:** Phase 6 §6a, Implementation Step 1.
- **Flaw:** `handle_create_call_session` (`screen_customer_360_activity.py:490-531`) accepts `task_id: str = Form(default="")` directly from the client with no verification that this task_id (a) exists, (b) belongs to `party_id`, or (c) belongs to the requesting staff. Phase 6a's whole anti-race mechanism is: "only when `task_id.strip()` is empty, call `task_svc.auto_claim_from_contact(...)`" (`phase-06-claim-policy-findings.md:45`) — i.e., presence of ANY non-empty `task_id` string suppresses the new auto-claim.
- **Failure scenario:** A client (buggy integration, browser devtools, or a staff member intentionally avoiding being tracked as "handling" a customer) submits `POST /api/parties/{party_id}/call-sessions` with `task_id=x` for any non-empty garbage value. Auto-claim is skipped entirely — silently reintroducing the exact "2 staff can both press Gọi on the same unclaimed customer" race that finding #9 and Phase 6a claim to close, with no error, no log line calling out the mismatch, and no downstream validation catching it (the draft is still created successfully since `activity_log.create_draft` is not shown validating `task_id` against `party_id` either).
- **Evidence:** `crm/src/adapters/inbound/web/screens/customer360/screen_customer_360_activity.py:490-521` (task_id is raw Form input, no lookup/validation before being used as a boolean gate). `screen_call_cockpit.py:156,181` shows the sibling `task_id` query param is similarly used only for UI pinning (`pinned_task_id = task_id.strip() or None`), reinforcing that nothing in this codepath treats `task_id` as an authenticated/verified reference.
- **Suggested fix:** Before skipping auto-claim, look up `task_id` and confirm it exists, belongs to `party_id`, and is assigned to `actor_id` (or at minimum exists and is open) — reject/ignore unrecognized `task_id` values rather than trusting presence-of-string as proof of "already in the structured task flow."

## Finding 4: Phase 3's safety assumption ("both call sites require a logged-in user") is contradicted by the code — `handle_log_activity` and the finalize API never enforce authentication
- **Severity:** Medium
- **Location:** Phase 3 ("Callback-Followup Task Assignee"), Risk Assessment section.
- **Flaw:** Phase 3's plan text states: *"if `actor_id` is `None`... shouldn't happen in practice since both call sites require a logged-in user"* (`phase-03-callback-followup-task-assignee.md:49`). This is factually wrong per the current code. `handle_create_call_session` is the **only** handler in this file that enforces authentication (`if not actor_id: return JSONResponse({"error": "unauthenticated"}, status_code=401)` — `screen_customer_360_activity.py:502-503`). Both callers of `execute_side_effects` — `handle_log_activity` (`:264-265`, no 401 branch) and the finalize API `handle_finalize_activity` (`:613-614`, no 401 branch) — derive `actor_id = current_user.user_id if current_user else None` and then proceed regardless of whether it's `None`.
- **Failure scenario:** If session/auth middleware upstream doesn't hard-block unauthenticated requests to these specific routes (not verified in this pass — router-level `Depends` wiring was out of scope), a request reaching `handle_log_activity`/`handle_finalize_activity` without a valid session creates activities, tasks, and (post-Phase-3) callback/follow-up tasks with `actor_id=None` → `assignee_user_id=None`, `created_by=None`. Phase 3 dismisses this as "not a regression, just a no-op safety fallback" — but the plan's own stated justification for treating it as low-risk is unverified and, per this grep pass, false for 2 of the 2 downstream callers of the function Phase 3 modifies.
- **Evidence:** `screen_customer_360_activity.py:264-265` (no 401 guard), `:502-503` (401 guard, contrast), `:613-614` (no 401 guard). `plans/.../phase-03-callback-followup-task-assignee.md:49`.
- **Suggested fix:** Either verify (and cite) the actual upstream auth-middleware guarantee that makes `current_user` non-None by the time these handlers run, or add the same explicit 401 check `handle_create_call_session` already has to `handle_log_activity`/`handle_finalize_activity` before shipping Phase 3 — don't ship an assignee-trust decision on an unverified premise.

## Finding 5: `caller`/`source` are unauthenticated, unbound client-declared strings that gate server response behavior — sets a weak trust-boundary precedent with no cross-check to actual request origin
- **Severity:** Medium
- **Location:** Phase 1 ("Redirect Context-Loss Fix"), Implementation Steps 3 and 8.
- **Flaw:** The fix for finding #1 is: `if caller.strip() in ("s01", "s14"): return HTMLResponse(content="")` (M05 POST, `phase-01-redirect-context-loss-fix.md:45`) and the parallel `elif source.strip() == "worklist": return HTMLResponse(content="")` (M08 POST, `:50`). Both `caller` and `source` are plain `Form()` string fields the client sets — there is no server-side binding to `Referer`, session state, or any signed/opaque token proving the request actually originated from S14/worklist. The plan's own Phase 1 Risk Assessment even flags this pattern is already precedent (`source == "call_cockpit"` is "currently dead code — no template sets it," meaning it was already speculatively trusted with nothing enforcing it).
- **Failure scenario:** This alone is low-impact (it only changes whether the client gets a redirect header or an empty 200 body — it does not change what gets written). But combined with Finding 1 and Finding 4, it demonstrates the pattern this plan is establishing across the touched surface: client-declared "context" strings (`caller`, `source`, `task_id`) are trusted for behavior-shaping decisions (skip redirect, skip auto-claim, select channel) without any of them being verified against actual server-known state (session, DB ownership, referer). None of the 7 phases add a verification layer for any of these fields. This is a maintainability/security-debt risk more than an immediate exploit: a future contributor extending this pattern (e.g., gating an actual write decision on `caller`/`source` instead of just response shape) would inherit an already-spoofable input with no established convention for validating it.
- **Evidence:** `phase-01-redirect-context-loss-fix.md:16,45,50` (`caller`/`source` as plain Form fields, `source == "call_cockpit"` cited as pre-existing unenforced trust). Cross-reference Findings 1, 3, 4 above (same unvalidated-client-input pattern recurring across Phases 1, 2, 3, 6).
- **Suggested fix:** No blocking change needed for Phase 1 alone (response-shape-only impact), but the plan should explicitly document that `caller`/`source`/`task_id` are UX hints, not security or authorization signals, and that no future phase should gate a write/authorization decision on them without adding real verification — this note is currently absent from every phase's Risk Assessment.

## Unresolved Questions
- Is there upstream auth middleware (not reviewed in this pass — out of scope for template/handler-level grep) that guarantees `current_user` is always set before `handle_log_activity`/`handle_finalize_activity` run? If yes, Finding 4 downgrades from "contradicted premise" to "the plan's citation is just imprecise, not wrong." Needs a router/middleware-level check before Phase 3 ships.
- Is this CRM treated as a fully-trusted single-tenant internal tool (all staff equally trusted, insider-threat-only model) or is there any intended per-staff data boundary? Findings 1-3 assume insider-threat matters (staff-to-staff sabotage/data-integrity risk) — if the product intent is "any staff can touch any customer's data, full stop," severities for Findings 1-3 should be recalibrated down from Critical/High to Medium, but the missing validation itself is still real and worth fixing given the plan's own stated goal (findings #2/#3/#9/#10 in the source report) is protecting per-customer signal integrity.
