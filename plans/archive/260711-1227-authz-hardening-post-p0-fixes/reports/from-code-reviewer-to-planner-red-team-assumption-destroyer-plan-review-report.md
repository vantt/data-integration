## Finding 1: Ownership check in Phase 2's `unclaim_customer_actions` is skipped entirely for unauthenticated/empty `actor_id`

- **Severity:** Critical
- **Location:** Phase 2, section "Implementation Steps", step 3
- **Flaw:** The plan's own pseudocode for the ownership gate is:
  > "If `actor_id` and not `self._authz.is_owner(existing.assignee_user_id, actor_id)` → return `"forbidden"`"

  This is `if actor_id and not is_owner(...)`. When `actor_id` is falsy (empty string), the whole condition short-circuits to `False` — the branch is **never entered**, and execution falls straight through to "Proceed with existing cancel logic," unclaiming the customer with **zero ownership check**. This is not equivalent to calling `is_owner("", "")` (which Phase 1's own code correctly returns `False` for) — the plan's guard skips the call to `is_owner` altogether rather than letting it fail closed.
- **Failure scenario:** `screen_worklist.py`'s `handle_unclaim_customer` (per Phase 2 step 5) derives `uid = _current_user_id(request)`, which research finding 3.1 confirms returns `""` when `request.state.current_user` is `None` (unauthenticated/session-not-populated). Unlike the plan's own cited precedent `handle_assign_me` (which does `if not uid: return 401` before proceeding), Phase 2 step 5 does **not** add an equivalent guard for the unclaim handler — it only validates `reason in VALID_UNCLAIM_REASONS`. So an unauthenticated (or session-expired) request with a valid `reason` unclaims ANY customer's claim, reintroducing exactly the IDOR this phase exists to close.
- **Evidence:** `plans/260711-1227-authz-hardening-post-p0-fixes/phase-02-unclaim-ownership-and-audit-trail.md` step 3 and step 5; `crm/src/adapters/inbound/web/screen_worklist.py:321-323` (`_current_user_id` returns `""` for no user); research `researcher-01-unclaim-ownership-audit-trail.md` §3 Finding 3.1 ("Line 442 (assign-me): uid = _current_user_id(request) → returns empty string if not authenticated → checked `if not uid: return 401`" — no equivalent check specified for unclaim).
- **Suggested fix:** Drop the `actor_id and` guard — call `self._authz.is_owner(existing.assignee_user_id, actor_id)` unconditionally (it already returns `False` for empty `actor_id`, which correctly yields `"forbidden"`). Additionally add an explicit `if not uid: return 401` (or equivalent) in both route handlers before calling `unclaim_customer_actions`, matching the `handle_assign_me` precedent the plan itself cites but doesn't apply.

## Finding 2: Phase 2 wires the raw `NoteRepository` into `TaskService` but the implementation pseudocode calls it with `NoteService`'s signature — will crash, and breaks the codebase's established single write-path convention

- **Severity:** Critical
- **Location:** Phase 2, sections "Architecture", "Related Code Files" (composition.py line), and "Implementation Steps" step 3-4
- **Flaw:** The plan's file list says: "Modify `crm/src/composition.py` (~line 328 ... add `sqlite_repos["note"]`)" — i.e. wire the **raw repository** (`SQLiteNoteRepository`, satisfying `NoteRepository` Protocol). But `NoteRepository.add_note` has signature `add_note(self, note: Note) -> None` — it takes one positional `Note` domain object, not kwargs. Step 3's pseudocode calls `self._notes_repo.add_note(...)` with `party_id`, `body`, `author_user_id=...`, `note_type=...`, `visibility=...` as separate kwargs — this is `NoteService.add_note`'s signature (`party_id, body, author_user_id=None, note_type="general", pinned=False, visibility="team", source_activity_id=None`), which additionally generates `note_id`/`created_at`, validates non-empty body, and commits. Calling the raw repo method with these kwargs raises `TypeError: add_note() got an unexpected keyword argument`.
- **Failure scenario:** Every existing `add_note` call site in the codebase goes through `NoteService` (never the raw repo directly): `activity_side_effects.py:184` (`notes.add_note(party_id, body, author_user_id=..., ...)` where `notes=services["note"]`, a `NoteService`), `screen_customer_360_notes.py:40` (same kwargs shape, `notes` = `NoteService`), `customer360_handler.py:218`. The raw repo's `add_note(note: Note)` is called from exactly one place: `NoteService.add_note` itself (`note_service.py:53`). Phase 2 would be the first and only caller in the codebase to bypass `NoteService` and call the raw repo directly — and it does so with the wrong call shape, so it fails at runtime, not just architecturally.
- **Evidence:** `crm/src/domain/ports/tag_repository.py:98-102` (`NoteRepository` Protocol, `add_note(self, note: Note) -> None`); `crm/src/adapters/outbound/sqlite/tag_note_repository.py:302-313` (concrete impl, single positional `note` param); `crm/src/application/note_service.py:30-56` (`NoteService.add_note` kwargs signature + validation + uuid/timestamp construction); `crm/src/composition.py:248` (`"note": SQLiteNoteRepository(db)` — raw repo) vs `crm/src/composition.py:323` (`"note": NoteService(sqlite_repos["note"], db)` — the service); grep confirms all 3 non-`NoteService`-internal callers of `.add_note(` use the `NoteService` kwargs shape.
- **Suggested fix:** Wire `services["note"]` (the `NoteService` instance) into `TaskService` as `notes_svc`, not `sqlite_repos["note"]`. Call `self._notes_svc.add_note(party_id, body, author_user_id=actor_id, note_type="unclaim_reason", visibility="team")` — matching every other caller in the codebase and getting validation/uuid/commit for free. The plan's own Risk Assessment flags this as an open question ("verify... whether TaskService should call a raw repository method or go through NoteService's own validation/business logic") but the Related Code Files / composition.py line and Implementation Steps sections present the raw-repo wiring as settled, which is the wrong answer per verified evidence.

## Finding 3: Phase 3's new required `party_id`/`authz` params on `resolve_actions_and_tasks`/`bulk_resolve` will break 20+ existing tests not listed in the phase's file list — directly contradicts the phase's own success criterion

- **Severity:** Critical
- **Location:** Phase 3, section "Related Code Files" (omission) vs. "Success Criteria" ("full existing bulk-resolve test suite still green")
- **Flaw:** Phase 3 makes `party_id: str` and `authz: AuthorizationService` **required** parameters on `resolve_actions_and_tasks()` and threads the same requirement into `outcome_resolve_helpers.bulk_resolve()`. Neither `crm/src/tests/test_outcome_bulk_resolve.py` nor `crm/src/tests/test_activity_disposition_api_routes.py` appears in Phase 3's "Related Code Files" list, yet both call these functions directly with bare `MagicMock()` `action_state` objects that have no `.resolve_party_id` configured.
- **Failure scenario:**
  - `test_outcome_bulk_resolve.py` has **~20 direct calls** to `_bulk_resolve(...)` (lines 82-223), none passing `party_id`/`authz` — these become `TypeError: missing required argument` immediately once the params are made required with no default, or (if defaulted) `action_state.resolve_party_id(aid)` returns an auto-generated `MagicMock()` attribute, which is `!= "expected_party_id"` under `is_same_party`'s `==` comparison — every `as_.dismiss.assert_called_once_with(...)` assertion in that file would then fail because dismiss/snooze gets silently skipped.
  - `test_activity_disposition_api_routes.py` lines 496-546 call `execute_side_effects(..., party_id="party-na-1", action_state=action_state, ..., resolve_action_ids=["a1"], resolve_task_ids=["t1"])` with `action_state = MagicMock()` (no `resolve_party_id` stub) — same silent-skip failure mode, breaking these 4 test blocks.
  - This directly contradicts Phase 3's own Success Criteria: "No behavior change for the all-valid-ids common case — full existing bulk-resolve test suite still green."
- **Evidence:** `crm/src/tests/test_outcome_bulk_resolve.py:82-223` (verified via grep, 20 `_bulk_resolve(` call sites, zero pass `party_id`/`authz`); `crm/src/tests/test_activity_disposition_api_routes.py:496,512,527,541` (`action_state = MagicMock()`, no `.resolve_party_id` stub) each followed by `execute_side_effects(...)` at 498,514,529,543 with `resolve_action_ids`/`resolve_task_ids` populated.
- **Suggested fix:** Add both test files to Phase 3's "Related Code Files" list; every existing `MagicMock()` `action_state`/`task_svc` fixture that exercises the resolve/dismiss/snooze path must be updated to stub `resolve_party_id`/`get_task(...).party_id` to return the matching `party_id` used in that test, or the tests must be re-audited case by case. Step 6 ("Grep for any OTHER caller... to confirm no other route/test needs updating") should be promoted from an implementation-time TODO to an explicit pre-verified file list — the grep was not actually run before the plan was written despite research covering these exact files.

## Finding 4: `AuthorizationService` DI pattern is genuinely inconsistent across its 3 real consumers, not just an implementation nuance — Phase 1's "single source of truth, wired once" claim doesn't hold for 2 of 3 call sites

- **Severity:** High
- **Location:** Phase 1 "Architecture"/"Risk Assessment" vs. Phase 3 "Implementation Steps" step 4-5
- **Flaw:** Phase 1 states the service will be "Wired once in `composition.py`, injected into whatever needs it" and frames this as the foundation that lets "findings #1 and #2 both consume" a single centralized instance. Verified call graph shows this cannot cleanly hold for Phase 3's consumer:
  - `execute_side_effects()` (`activity_side_effects.py:93-112`) — the function that internally calls `resolve_actions_and_tasks()` at line 246 — has **no** `authz` parameter today, and its only caller in `screen_customer_360_activity.py`'s `_run_side_effects` closure (lines 73-83) hardcodes a fixed kwarg list (`profile`, `notes`, `task_svc`, `party_insights`, `action_state`) that does not include anything authz-shaped.
  - `outcome_resolve_helpers.bulk_resolve()` is explicitly documented as "No FastAPI / web dependency — imported by both the activity routes module and the pure-logic unit tests (which run outside Docker where fastapi is absent)" (`outcome_resolve_helpers.py:1-5`) — it currently has zero DI wiring of any kind (all params are duck-typed, no composition.py involvement at all for this module).
  - Threading `authz` from `composition.py` down to both of these real call sites (not just `TaskService`'s constructor, which is the only site Phase 1's plan actually verified) requires new required params on `execute_side_effects`, on `_run_side_effects`, on `register_activity_routes`'s factory signature, and on `bulk_resolve`/its caller `handle_resolve_async` — **none of these intermediate files are in Phase 3's Related Code Files list.**
  - The plan's stated fallback — "inline construction (`AuthorizationService()`) at the call site is an acceptable fallback" — means, if taken (likely, given the threading depth above), the composition.py-wired instance from Phase 1 step 3 is **never actually used** by 2 of the 3 real consumers (`execute_side_effects` step 7, `bulk_resolve`), only by `TaskService`. That undercuts Phase 1's own architecture rationale ("a future RBAC upgrade should not need to touch [call sites]... when real RBAC work happens later, it extends this service's methods rather than requiring every call site to be found and rewired individually") — if `AuthorizationService` later needs real IO (a role table, a policy lookup), the 2 inline-constructed call sites are exactly the "N call sites scattered across the codebase" scenario Phase 1 claims to prevent, because they were never wired through DI in the first place.
- **Evidence:** `crm/src/application/activity_side_effects.py:93-112` (no `authz` param), `:246` (internal call to `resolve_actions_and_tasks` with 6 positional args, no `party_id`/`authz`); `crm/src/adapters/inbound/web/screens/customer360/screen_customer_360_activity.py:73-83` (`_run_side_effects` closure, fixed kwarg list); `crm/src/adapters/inbound/web/screens/customer360/outcome_resolve_helpers.py:1-9` (pure-logic, no-FastAPI docstring, zero DI).
- **Suggested fix:** Either (a) commit to full DI threading and add the 3-4 missing intermediate files to Phase 3's Related Code Files (composition.py → `make_customer_360_router` → `register_activity_routes` → `_run_side_effects` → `execute_side_effects`; and composition.py or route-handler-level → `handle_resolve_async` → `bulk_resolve`), or (b) explicitly acknowledge in Phase 1 that `AuthorizationService` is cheap enough to be constructed ad-hoc at every pure-function call site and drop the "wired once, single source of truth" framing — don't claim an architectural property the actual call graph doesn't support.

## Finding 5: `VALID_UNCLAIM_REASONS` as (code, VN-label) pairs contradicts the very naming/shape convention the plan claims to follow

- **Severity:** Medium
- **Location:** Phase 2, "Related Code Files" (task.py entry) and "Implementation Steps" step 1
- **Flaw:** The plan states: "add `VALID_UNCLAIM_REASONS` constant list, matching `activity.py`'s `VALID_OUTCOME_REASONS` placement/naming convention" — then in step 1 describes it as "short fixed list with VN labels, e.g. `wrong_region` (`"Ngoài khu vực phụ trách"`), ...". Verified: `VALID_OUTCOME_REASONS` (`activity.py:60-78`) is a **flat list of bare code strings** with no embedded labels — VN labels for those reasons live in the template layer (`c360_call_cockpit_panel.html:822`), not the domain constant. Same pattern for `task.py`'s existing `VALID_TASK_STATUSES`/`VALID_TASK_KINDS`/`VALID_TASK_SOURCES` (all flat code lists, verified via grep). The plan's own example (code+label tuples) is a different data shape than every existing "VALID_*" constant in this codebase, despite claiming to match the convention.
- **Failure scenario:** Not a functional break by itself, but it pushes UI-facing text into the domain layer against this codebase's established layering (domain = codes only, templates = labels), and step 7's own hedge ("check whether other reason-pickers in this codebase pass the list via context or hardcode; match that convention") shows the plan itself hasn't resolved which shape to actually build.
- **Evidence:** `crm/src/domain/entities/activity.py:60-78` (flat `VALID_OUTCOME_REASONS` list); `crm/src/domain/entities/task.py:13-39` (flat `VALID_TASK_STATUSES`/`VALID_TASK_KINDS`/`VALID_TASK_SOURCES`, no labels); `crm/src/adapters/inbound/web/templates/fragments/c360_call_cockpit_panel.html:822` (VN labels live in template, not domain).
- **Suggested fix:** Keep `VALID_UNCLAIM_REASONS` as a flat code list (`["wrong_region", "wrong_specialty", "duplicate_lead", "reassign_colleague", "other"]`), hardcode VN labels in the 2 templates directly (matching the outcome-reason precedent), not in the domain constant.

## Finding 6: Stale `TaskClaimWriter` Protocol in `screen_worklist.py` not updated for the new 3-state return type

- **Severity:** Medium
- **Location:** Phase 2, "Related Code Files" (omission)
- **Flaw:** `screen_worklist.py:75-77` defines a local structural `Protocol` for the worklist router's `task_claim` dependency:
  ```python
  class TaskClaimWriter(Protocol):
      def claim_customer_actions(self, party_id: str, actions: list, assignee_id: str) -> tuple: ...
      def unclaim_customer_actions(self, party_id: str) -> bool: ...
  ```
  Phase 2 changes `TaskService.unclaim_customer_actions` to `(self, party_id: str, actor_id: Optional[str] = None, reason: Optional[str] = None) -> str` (3-state result). This Protocol declaration is not in Phase 2's Related Code Files and is never updated, leaving the documented DI contract for this router factory silently wrong (declares `-> bool`, actual implementation returns `-> str`).
- **Failure scenario:** No CI/mypy enforcement found in this repo (no mypy config), so this won't fail a build, but it's exactly the kind of stale-contract drift the plan's own Risk Assessment worries about for callers doing "bare truthiness checks" — a future reader/maintainer trusting this Protocol's `-> bool` signature could reintroduce the bug the plan's own Risk Assessment explicitly warns against.
- **Evidence:** `crm/src/adapters/inbound/web/screen_worklist.py:75-77`.
- **Suggested fix:** Add `screen_worklist.py`'s `TaskClaimWriter` Protocol update (`-> str`, add `actor_id`/`reason` params) to Phase 2's Related Code Files.
